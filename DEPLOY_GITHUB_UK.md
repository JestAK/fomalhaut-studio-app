# Автоматичні оновлення з GitHub

Після налаштування зміни в `main` проходитимуть тести та автоматично встановлюватимуться на ваш AWS-сервер. До ввімкнення `DEPLOY_ENABLED` працюють лише перевірки. Живе розгортання потребує одноразового налаштування нижче.

## 1. Підготувати сервер

У терміналі AWS (де ви входите як `ubuntu`):

```bash
mkdir -p ~/fomalhaut-deploy/releases
chmod 700 ~/fomalhaut-deploy
cp ~/releases/v34/Fomalhaut-Studio/.env ~/fomalhaut-deploy/shared.env
chmod 600 ~/fomalhaut-deploy/shared.env
sudo -n docker ps
```

Якщо активна версія інша, замініть `v34` на її каталог. Копіюйте саме чинну `.env`. Не змінюйте `COMPOSE_PROJECT_NAME`: він визначає наявні томи БД та файлів. Не виконуйте `docker compose down -v`.

Остання команда має спрацювати без запиту пароля. Сценарій використовує `sudo -n bash ops/update.sh`; користувач деплою повинен мати відповідні права. Ключ такого користувача дає значні права на сервері — використовуйте окремий ключ тільки для деплою.

## 2. Створити окремий SSH-ключ

На своєму комп'ютері:

```bash
ssh-keygen -t ed25519 -f fomalhaut-deploy -C github-actions-fomalhaut
```

Для автоматичного входу залиште парольну фразу порожньою. Отримаєте два файли: `fomalhaut-deploy` (секретний) та `fomalhaut-deploy.pub` (публічний).

На сервері:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys
```

Додайте в кінець окремим рядком вміст `.pub`, перед `ssh-ed25519` поставте `restrict ` (із пробілом). Збережіть Ctrl+O, Enter, Ctrl+X, потім:

```bash
chmod 600 ~/.ssh/authorized_keys
```

Секретний ключ не надсилайте в чат і не додавайте до репозиторію.

## 3. Отримати ключ самого сервера

У довіреному терміналі AWS:

```bash
sudo cat /etc/ssh/ssh_host_ed25519_key.pub
```

Сформуйте рядок для `DEPLOY_KNOWN_HOSTS`:

```text
YOUR_PUBLIC_HOST ssh-ed25519 AAAA...значення_з_команди...
```

Першим полем має бути та сама публічна IP-адреса або домен, що й у `DEPLOY_HOST`. Не використовуйте внутрішню адресу `172.26...`. Порт SSH 22 має бути доступний GitHub runner; якщо firewall дозволяє лише вашу IP-адресу, потрібен окремо налаштований доступ для runner. Не вимикайте перевірку ключа сервера.

## 4. Додати секрети в GitHub

Відкрийте репозиторій → Settings → Environments → New environment → `production`. Обмежте deployment branches гілкою `main`. Додайте Environment secrets:

| Назва | Значення |
| --- | --- |
| `DEPLOY_HOST` | Публічна IP-адреса або домен сервера без `https://` |
| `DEPLOY_USER` | `ubuntu` |
| `DEPLOY_SSH_KEY` | Увесь секретний файл `fomalhaut-deploy`, включно з BEGIN/END |
| `DEPLOY_KNOWN_HOSTS` | Рядок із попереднього кроку |

Після цього Settings → Secrets and variables → Actions → Variables → New repository variable:

```text
Name: DEPLOY_ENABLED
Value: true
```

Не додавайте токени Telegram/Notion до YAML: вони залишаються у `~/fomalhaut-deploy/shared.env` на сервері.

## 5. Перше оновлення

Actions → Test and deploy → Run workflow → `main`. Дочекайтеся зелених `test` і `deploy`. Після цього перевірте вхід у додаток, файли та сповіщення. Саме цей запуск перевірить живий SSH-доступ та AWS.

Наступні push у `main` оновлюватимуть сервер автоматично. Не запускайте старі workflow вручну, якщо не хочете встановити старий код.

Сценарій завантажує архів, звіряє SHA-256, бере блокування від паралельних деплоїв, збирає образ, чекає чергу файлів, резервує БД та перевіряє здоров'я нового сервера. Він не видаляє Docker volumes.

## Де лежать файли та як відкотитися

- `~/fomalhaut-deploy/shared.env` — конфігурація для наступних релізів.
- `~/fomalhaut-deploy/current` — останній успішний реліз.
- `~/fomalhaut-deploy/previous` — попередній успішний реліз після другого деплою.
- `~/fomalhaut-deploy/releases/` — релізи та їхні резервні копії.

Стежте за вільним місцем: старі релізи та резерви автоматично не видаляються. Першу попередню версію збережіть у її старому каталозі `~/releases/...`.

При помилці перегляньте Actions → невдалий крок. На сервері в каталозі відповідного релізу: `sudo docker compose logs --tail=100 studio`.

Автоматичного відкату БД немає. Для повернення сумісного старого коду запустіть `sudo bash ops/update.sh` з його каталогу; якщо змінилася структура БД, спершу дотримуйтесь інструкції відновлення резерву в документації проєкту. Симлінк `current` після невдалого деплою не гарантує, що старий контейнер ще працює.

Щоб зупинити автодеплой, змініть `DEPLOY_ENABLED` на `false`. Поточний додаток продовжить працювати.
