# Запуск Fomalhaut Studio на AWS

Це повний код, не лише демка. У комплекті Docker Compose, Node 24, SQLite, обробка аудіо, локальний Telegram Bot API, Caddy HTTPS, резервування й оновлення.

## 1. Окремий тестовий простір

Створіть окремого бота в офіційному @BotFather командою /newbot. Збережіть token лише у .env на сервері. Створіть приватну Telegram-супергрупу, увімкніть теми, додайте бота адміністратором і запросіть 2–3 тестувальників. Поки не підключайте основний чат команди.

На https://my.telegram.org у API development tools отримайте api_id і api_hash для локального Bot API. Це не токен BotFather. Не надсилайте ці секрети в чат.

## 2. Сервер

Практична стартова конфігурація: AWS Lightsail, Linux/Ubuntu 24.04, x86_64, 2 vCPU, 4 ГБ RAM, від 40 ГБ диска. Це орієнтир, а не виміряний мінімум. Можна EC2 із аналогічною конфігурацією. Перевірте ціну й доступні кредити в AWS перед створенням: безкоштовність не гарантована. Створіть бюджетне сповіщення AWS.

Прив’яжіть Static IP (Lightsail) або Elastic IP (EC2). У firewall / Security Group дозвольте TCP 80,443 з інтернету, SSH 22 лише зі своєї IP. Не відкривайте 3000 і 8081. Створіть DNS A-запис studio-test.ВАШ-ДОМЕН на IP сервера. Домен потрібен для HTTPS.

Установіть Docker Engine та Compose plugin за https://docs.docker.com/engine/install/ubuntu/ . Перевірте `docker compose version`. Надалі команди виконуються користувачем із доступом до Docker (або з sudo).

Завантажте ZIP на сервер через SFTP/SCP, розпакуйте та перейдіть в Fomalhaut-Studio:

```bash
unzip Fomalhaut-Studio.zip
cd Fomalhaut-Studio
cp .env.example .env
chmod 600 .env
nano .env
docker compose build studio
```

Заповніть BOT_TOKEN, TELEGRAM_API_ID, TELEGRAM_API_HASH, APP_DOMAIN (без https), APP_URL (https://домен), ADMIN_IDS (числові ID через кому), TEAM_CHAT_ID (числовий -100…). COMPOSE_PROJECT_NAME не змінюйте між оновленнями.

Щоб отримати ID без сторонніх ботів: після додавання бота адміністратором напишіть йому /start у приватному чаті та повідомлення в тестовій групі. До запуску застосунку й до prepare-bot виконайте:

```bash
docker compose run --rm --no-deps studio node server/setup-ids.mjs
```

Скрипт показує user_id і chat_id побачених повідомлень. Якщо порожньо — надішліть нові повідомлення і повторіть. Якщо бот уже працює на локальному API, цей допоміжний хмарний запит не підходить. Не запускайте два polling-процеси одного бота.

Запишіть ID у .env, потім:

```bash
docker compose run --rm --no-deps studio node server/prepare-bot.mjs
docker compose up -d
docker compose ps
docker compose logs --tail=100 studio
```

prepare-bot переводить бота з хмарного API на локальний. Caddy отримує HTTPS-сертифікат автоматично за правильного DNS і доступних 80/443. Healthcheck: https://ВАШ-ДОМЕН/api/health .

## 3. Реєстрація Mini App

У BotFather: /mybots → ваш бот → налаштування Main Mini App → адреса APP_URL. Додатково /setmenubutton → виберіть бота → текст «Студія» → той самий HTTPS URL. Відкривайте застосунок кнопкою бота або https://t.me/ІМЯ_БОТА?startapp . Окрема публікація в магазині застосунків не потрібна.

Вхід працює в Telegram Mini App і у звичайному браузері після налаштування Telegram Login (розділ 8). Публічна Sites-демка — окремий демонстраційний режим.

## 4. Перевірка перед командою

1. Увійдіть через Telegram під ADMIN_IDS, дозвольте повідомлення боту. Тестувальники мають бути в тестовій групі; схваліть їх у «Команда», призначте ролі.
2. Створіть проєкт із унікальним кодом і двома серіями. Призначте перекладача, редактора, рольовика, акторів, правкера та звукаря.
3. Створіть тему в групі. У налаштуваннях проєкту прив’яжіть посилання на повідомлення всередині теми.
4. У списку етапів встановіть ручний запуск редактури. Почніть серію, здайте переклад. Перевірте, що редактор не отримує активне завдання до дозволу адміна.
5. Рольовиком роздайте два ASS, перевірте розпізнавання й таблицю одержувачів. Актором надішліть короткі стерео WAV 16-bit, WAV 24-bit та FLAC. Завантажте результат із Telegram, перевірте в REAPER: mono, та сама частота й бітність, коректна назва.
6. Перевірте заміну файла, повідомлення правкеру, «Є правки/Немає правок», FIX та FIX2, вибір файлів у ZIP, завершення зведення й автозапуск наступної серії. Окремо достроково запустіть серію, щоб перевірити відсутність дублів.
7. Перезапустіть контейнери: користувачі, файли, строки й статуси мають залишитися. Створіть резерв і перевірте відновлення на окремому тестовому сервері.

У коді є автоматичні тести (`npm test` під Node 24 з FFmpeg і zip). Живий AWS/Telegram і міграцію між VPS у вашому оточенні ще треба перевірити.

## 5. Аудіо

Сервер приймає WAV/FLAC і робить mono FLAC. Стерео зводиться як (L+R)/2; нормалізація гучності, шумодав і зміна частоти не застосовуються. У цьому релізі перевірене збереження 16/24-bit PCM. 8/32-bit integer та 32/64-bit float відхиляються, а не непомітно перетворюються в 24-bit. Float неможливо представити у FLAC без зміни числового формату. Це обмеження релізу, не вимога, прихована від вас.

Неймінг: код_Eсерія_нік_етап_vверсія.flac; правки містять FIX, FIX2 тощо. Зведення в mono саме по собі змінює стереосигнал.

## 6. Оновлення та переїзд

Оновлення: розпакуйте нову версію в нову теку, скопіюйте чинний .env, збережіть COMPOSE_PROJECT_NAME і виконайте `bash ops/update.sh`. Скрипт призупиняє зміни, чекає чергу, робить backup і замінює Studio. Не використовуйте `docker compose down -v` — це видаляє volumes.

Для переїзду дотримуйтеся повної процедури в README_UK.md, розділ про перенесення. Потрібні SQLite, .env, той самий бот і Telegram-група; файли залишаються в Telegram, але індекс і налаштування живуть у SQLite. Один лише чат не відновить усі статуси.

Зробіть `bash ops/backup.sh`, скачайте резерв поза VPS. Перед фінальним backup припиніть прийом змін, дочекайтеся черги. Зупиніть старий Studio. Локальний Bot API переносіть за процедурою close/зупинки в README; два сервери одного бота одночасно не запускайте. На новому чистому сервері: код, Docker, `bash ops/restore.sh /шлях/до/резерву`, перевірка .env, зміна DNS, запуск. Збережіть старий сервер і резерв до перевірки нового. API ID/hash, bot token і власний домен дозволяють переїхати з AWS до іншого провайдера.

Після тестів для реальної команди краще створити окремого production-бота, production-групу/тему й чисту базу з окремим COMPOSE_PROJECT_NAME. Налаштування команди внесіть заново, не змішуйте тестові записи з робочими.

Офіційні довідки: https://core.telegram.org/bots/features , https://core.telegram.org/bots/webapps , https://docs.aws.amazon.com/lightsail/latest/userguide/lightsail-create-static-ip.html .

## 7. Журнали помилок

Сервер пише структуровані JSON-журнали в Docker: час UTC, рівень, подія, ID запиту/обробки файла, тривалість, статус та місця збою в коді. Тіла запитів, заголовки, URL, імена файлів, токени та тексти зовнішніх помилок не записуються. HTTP-помилка містить request_id; той самий ID є в заголовку X-Request-ID. ID можна знайти у Network браузера і за ним зіставити журнали.

```bash
# Останні події застосунку
docker compose logs --since=1h --tail=200 studio
# Стежити наживо
docker compose logs -f --tail=100 studio
# Лише помилки застосунку
docker compose logs --since=24h studio | grep '"level":"error"'
# Зберегти журнал для розбору
docker compose logs --since=1h --no-color studio > studio-errors.log
```

Події: http.failed/http.complete/http.aborted, job.started/job.completed/job.failed, telegram.poll_failed, notification.failed, maintenance.failed, process.fatal. У job.failed фаза delivery_uncertain означає, що доставка могла відбутися: спочатку перевірте Telegram, щоб не створити дубль. Очікувані відмови 4xx мають рівень warn. LOG_LEVEL у .env: info (типово), warn або error. Після зміни виконайте `docker compose up -d studio`.

Docker обмежує журнали кожного з трьох сервісів трьома файлами по 10 МБ (приблизно 90 МБ сумарно). Це ротація за розміром, а не гарантована кількість днів. Журнали переживають restart, але можуть зникнути при перевстворенні контейнера: перед оновленням збережіть потрібний фрагмент командою вище. Для аварій через нестачу RAM також перевіряйте `docker inspect --format '{{.State.OOMKilled}}' "$(docker compose ps -q studio)"`: процес, убитий ОС, може не встигнути записати помилку. Журнали telegram-bot-api/caddy — окремі журнали сторонніх сервісів; не поширюйте їх без перевірки на секрети.


## 8. Вхід зі звичайного браузера

Цей реліз додає офіційний Telegram Login SDK. Звичайний браузер і Mini App використовують одну базу користувачів, ролей і завдань. Вхід не дає автоматичного доступу: перевіряється членство в командній групі, блокування та схвалення адміном. Сесія діє 12 годин у поточній вкладці браузера; є кнопка «Вийти». Після завершення сесії оновіть сторінку й увійдіть знову.

1. У мініапці офіційного BotFather виберіть свого бота → Login Widget.
2. У Allowed URLs додайте повну адресу origin сайту: наприклад https://fomalhaut-manager.duckdns.org (без /api/health). Використовуйте свій фактичний домен. Реєструвати callback URI для цього SDK-варіанта не потрібно.
3. Скопіюйте Client ID. У Advanced залиште алгоритм RS256. Client Secret для нашого SDK-варіанта не використовується: не вставляйте його у фронтенд. TELEGRAM_API_ID з my.telegram.org — інший параметр.
4. У .env додайте TELEGRAM_LOGIN_CLIENT_ID=числовий_Client_ID. Цей параметр необов’язковий: без нього Mini App працює, а браузер показує пояснення, що вхід ще не налаштований.
5. Застосуйте оновлення зі збереженням volumes. Відкрийте свій HTTPS URL у Chrome/Firefox/Edge, натисніть «Увійти через Telegram», дозвольте popup, підтвердьте акаунт у Telegram. Новому користувачу адмін має схвалити доступ; потім він повторює вхід.
6. Перевірте, що в браузері видно ті самі завдання, що в Mini App; перевірте «Вийти» та повторний вхід. Блокування акаунта й видалення з групи мають забороняти запити також у браузері.

Сервер перевіряє RS256-підпис за офіційними ключами Telegram, issuer, audience, строк дії та одноразовий nonce, прив’язаний до захищеного cookie браузера. Сторонній origin відхиляється. Токен входу й cookie не записуються в журнали. Дозволяйте cookies для сайту та popup Telegram. Реальну авторизацію на вашому домені потрібно перевірити після налаштування BotFather; автоматичні тести не замінюють її.

### Оновлення саме з першого встановленого пакета

Не видаляйте стару папку та volumes. Завантажте новий ZIP у /home/ubuntu/Fomalhaut-Studio-browser.zip (наприклад через scp). Виконайте послідовно:

```bash
cd ~/releases/initial/Fomalhaut-Studio
sudo bash ops/backup.sh
mkdir -p ~/releases/browser-login
unzip ~/Fomalhaut-Studio-browser.zip -d ~/releases/browser-login
cp .env ~/releases/browser-login/Fomalhaut-Studio/.env
cd ~/releases/browser-login/Fomalhaut-Studio
chmod 600 .env
nano .env
```

Додайте TELEGRAM_LOGIN_CLIENT_ID, перевірте справжні TEAM_CHAT_ID та ADMIN_IDS. Не копіюйте приклади замість чинних секретів. Збережіть COMPOSE_PROJECT_NAME=fomalhaut-studio таким самим, як у початковій установці. Потім:

```bash
sudo bash ops/update.sh
sudo docker compose ps
sudo docker compose logs --tail=50 studio
```

Цей реліз містить актуальні setup-ids, логування і виправлення запуску з одним адміністратором. Повторно запускати prepare-bot або отримувати api_id/api_hash не потрібно. База та Telegram Bot API використовують чинні volumes. Якщо update.sh завершується помилкою — збережіть її текст, не видаляйте volumes і не запускайте restore поверх чинної бази.

Онбординг автоматично показується один раз на акаунт. Позначка першого показу зберігається на сервері до відкриття знайомства: закриття хрестиком або «Пропустити» не спричиняє повторний автоматичний показ. Інший пристрій, браузер чи повторний вхід не скидають позначку. У меню акаунта знайомство можна відкрити вручну. Стару позначку з браузера перенесено в профіль під час входу з цього браузера; якщо вона залишилася лише на іншому пристрої, сервер ще не може її знати.
